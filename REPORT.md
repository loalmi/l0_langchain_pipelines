## 1. Цель работы
Научиться строить пайплайн интеллектуального интерфейса, в котором LLM интерпретирует запрос на естественном языке и возвращает параметры в строгом формате (Structured Output или Tool Call), а классическая программа (Python + SQLite) проверяет эти параметры и выполняет поиск. Также отработать механизмы обработки ошибок (retry), логирования и хранения состояния диалога.

## 2. Краткое описание архитектуры
Решение построено на базе LangChain Expression Language (LCEL). Основной пайплайн состоит из следующих этапов:
1. **Prompt:** `ChatPromptTemplate` формирует запрос с инструкциями и схемой JSON (через `PydanticOutputParser`).
2. **LLM:** Вызов модели `qwen3.8-27b` (с отключенным режимом размышления для стабильности, кроме спец. заданий).
3. **Parser:** Валидация ответа через Pydantic-модель `ProductQuery`.
4. **Retry:** Механизм `with_retry` перехватывает `OutputParserException` и повторяет *только* этапы LLM+Parser (до 3 раз), не дергая базу данных.
5. **Action:** Python-функция `search_products` принимает валидированный объект, формирует безопасный параметризованный SQL-запрос к SQLite и возвращает результат.
6. **State Management:** Для уточняющих запросов используется хранение последнего валидного состояния `ProductQuery` вне модели.

## 3. Результаты выполнения заданий

### Часть 1. Базовая цепочка LangChain
Создана параметризованная цепочка `prompt | llm | StrOutputParser()`. 
**Сравнение типов:** Прямой вызов `llm.invoke()` возвращает объект `<class 'langchain_core.messages.ai.AIMessage'>`, тогда как вызов цепочки с `StrOutputParser` сразу возвращает готовую строку (`<class 'str'>`), что упрощает дальнейшую обработку без необходимости извлекать атрибут `.content`. Batch-обработка 3-х запросов прошла успешно.

### Часть 2. Structured Output и Pydantic
Описана модель `ProductQuery` с полями `category` (Literal), `max_price` (Optional[int], ge=0) и `sort_by` (Literal). 

**Анализ неоднозначных запросов (Задание 2.3):**
- *«Что-нибудь недорогое для работы, но не телефон»* → Модель угадала `category='laptop'`, `max_price=50000`.
- *«Покажи топовые варианты, но чтобы не слишком дорого»* → Модель вернула `category='other'`, `max_price=null`.
**Вывод:** При отсутствии явных "якорей" модель либо галлюцинирует (подставляет дефолтные значения), либо откатывается к `other`. В реальной системе такие запросы требуют диалога уточнения, а не слепого поиска.

**Сравнение режима размышления (Задание 2.4):**
| Параметр | Reasoning OFF | Reasoning ON |
| :--- | :--- | :--- |
| Время ответа | ~1.6 – 2.7 сек | ~3.3 – 9.2 сек |
| Токены (output) | ~35-40 | ~350-600 (из них >300 `reasoning_tokens`) |
| Содержимое `content` | Чистый JSON (иногда с ```) | Часто содержит блок рассуждений перед JSON |
| Работа парсера | Успешно | Успешно (PydanticOutputParser умеет извлекать JSON из текста) |

**Вывод:** Режим размышления значительно увеличивает время и стоимость (токены), но для простых задач извлечения сущностей он избыточен. Парсер при этом успешно справляется с "мусором" вокруг JSON.

### Часть 3. Вызов классического программного обеспечения
Создана БД SQLite с 15+ товарами. Функция поиска использует параметризованные SQL-запросы (защита от инъекций). Если `category='other'`, поиск не выполняется, возвращается сообщение об уточнении категории.

**Сравнение: с базой и без базы (Задание 3.3)**
| Запрос пользователя | Ответ LLM без доступа к БД | Результат пайплайна с БД | Корректность |
| :--- | :--- | :--- | :--- |
| Какие ноутбуки дешевле 70 000 ₽ есть в каталоге? | Отказ: «У меня нет доступа к вашему текущему каталогу...» | Lenovo IdeaPad 3 (45000), ASUS VivoBook 15 (58000), Acer Aspire 5 (62000) | ✅ 100% |
| Какие самые дорогие смартфоны есть в каталоге? | Отказ: «Предоставьте список товаров» | iPhone 15 Pro (130000), Galaxy S23 (95000) и др. | ✅ 100% |
| Какие планшеты есть в каталоге? | Отказ: «У меня нет доступа к каталогу» | Galaxy Tab S9, iPad 10, Xiaomi Pad 6 и др. | ✅ 100% |

**Сравнение подходов: Инструкции формата vs Инструменты (Задание 3.4)**
- **Structured Output (Часть 2):** Мы *заставляем* модель выдать JSON в основном тексте ответа. Парсинг происходит жестко.
- **Tools (Часть 3.4):** Мы даем модели *выбор*. Она может просто ответить текстом («Привет! Как дела?»), а может сформировать `tool_calls`. Схема валидируется фреймворком LangChain до вызова функции. Это более гибкий и "агентский" подход.

### Часть 4. Retry и журнал выполнения
**Анализ ошибок парсинга (Задание 4.1):**
1. **Синтаксическая ошибка JSON** (`{"category": "laptop", "max_price": 70000,}`): Вызывает `OutputParserException` с причиной `JSONDecodeError` (ожидалось имя свойства из-за лишней запятой).
2. **Нарушение перечисления** (`"category": "fridge"`): Вызывает `OutputParserException` с причиной Pydantic `ValidationError` (`literal_error`).
3. **Нарушение ограничений** (`"max_price": -100`): Вызывает `OutputParserException` с причиной Pydantic `ValidationError` (`greater_than_equal`).

**Механизм Retry (Задание 4.2, 4.4):**
Цепочка настроена как `(prompt | llm | parser).with_retry(stop_after_attempt=3, retry_if_exception_type=(OutputParserException,))`. 
Для гарантированной проверки использовалась `FakeListChatModel`. 
- *Сценарий "Ошибка -> Успех":* Журнал показывает `attempt: 1` (parse_error), затем `attempt: 2` (parse_ok), после чего **однократно** вызывается поиск.
- *Сценарий "3 ошибки":* Журнал фиксирует 3 попытки `parse_error`, после чего пайплайн корректно завершается с понятным сообщением об ошибке, не выполняя SQL-запрос.

**Фрагмент журнала (успешный retry):**
```json
{"time": "2026-11-10T23:26:19", "step": "llm_call_start", "attempt": 1}
{"time": "2026-11-10T23:26:19", "step": "parse_error", "error_type": "OutputParserException"}
{"time": "2026-11-10T23:26:21", "step": "llm_call_start", "attempt": 2}
{"time": "2026-11-10T23:26:21", "step": "parse_ok", "category": "laptop", "max_price": 70000}
{"time": "2026-11-10T23:26:21", "step": "params_validated", "params": {"category": "laptop", "max_price": 70000}}
{"time": "2026-11-10T23:26:21", "step": "search_done", "found": 3}
```
### Часть 5. Уточняющие запросы

#### Задание 5.1. Состояние вне модели
Для поддержки уточняющих запросов была реализована переменная `current_query`, хранящая последний валидный объект `ProductQuery`. При новом запросе модели передаётся не только реплика пользователя, но и JSON-представление предыдущего состояния (`prev_json`). 

**Пример диалога:**
1. *«Покажи ноутбуки до 80 тысяч»* → `category='laptop'`, `max_price=80000`, `sort_by='price_desc'`
2. *«А сначала дешёвые?»* → `category='laptop'`, `max_price=80000`, `sort_by='price_asc'` (цена сохранена, изменена сортировка)
3. *«А что есть среди смартфонов?»* → `category='smartphone'`, `max_price=80000`, `sort_by='price_asc'` (категория изменена, но лимит цены и сортировка **сохранились**).

#### Задание 5.2. Сравнение с историей диалога
Был реализован альтернативный вариант, где в промпт передаётся весь текст истории диалога, а не только текущий JSON-стейт. Сравнение двух подходов на двух диалогах показало следующие результаты:

| Диалог / Реплика | Подход А: Передача состояния (JSON) | Подход Б: Передача всей истории |
| :--- | :--- | :--- |
| **Диалог 1:**<br>1. Ноутбуки до 80к<br>2. А сначала дешёвые?<br>3. А что среди смартфонов? | Сохранил `max_price=80000` при смене категории. Параметры обновляются предсказуемо. | **Сбросил** `max_price` в `None`. Модель интерпретировала смену категории как начало нового поиска с нуля, проигнорировав предыдущий контекст цены. |
| **Диалог 2:**<br>1. Хочу планшет<br>2. Не дороже 40 тысяч<br>3. А самые дорогие из них? | Корректно обновил сортировку, сохранив категорию и цену. | Корректно обновил параметры, но... |
| **Расход токенов (input)** | Стабильный (~400-420 токенов на шаг), так как промпт имеет фиксированный размер. | Растущий (409 → 422 → 440+ токенов), так как с каждым шагом в промпт добавляется новый текст. |

**Вывод по части 5:** Хранение структурированного состояния вне модели (Подход А) является значительно более надёжным для параметрического поиска. Оно предотвращает «забывание» контекстных ограничений моделью и экономит входные токены, избегая разрастания промпта.

## 4. Общие выводы

В ходе выполнения лабораторной работы был разработан и протестирован устойчивый пайплайн интеллектуального интерфейса к каталогу товаров. 

Ключевые итоги:
1. **Валидация обязательна:** LLM не может гарантировать идеальный JSON. Использование `Pydantic` в связке с механизмом `with_retry` делает пайплайн устойчивым к галлюцинациям формата, не допуская выполнения некорректного кода.
2. **Разделение ответственности:** LLM должна только *извлекать намерения* и параметры, а не генерировать SQL-код. Параметризованные запросы в классическом Python-коде гарантируют безопасность (защита от инъекций) и детерминированность результатов.
3. **Управление состоянием:** Для многошаговых сценариев с уточнениями передача текущего состояния (JSON-объекта) работает стабильнее и дешевле, чем скармливание модели всей истории переписки, которая может запутать модель и увеличить расход токенов.
4. **Инструменты vs Формат:** Подход с `bind_tools` является более гибким и «агентским» решением по сравнению с жёстким `PydanticOutputParser`, так как позволяет модели самой решать, когда нужны данные извне, а когда можно ответить обычным текстом (например, на приветствие).
